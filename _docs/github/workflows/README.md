## Key Components

- **`dbt CD workflow`** (in `dbt-cd.yml`) — This workflow implements the repository's continuous deployment job that runs on pushes to main and performs a dbt build against a local DuckDB live environment, making it the primary automated path for deploying model changes.
- **`dbt CI workflow`** (in `dbt-ci.yml`) — This workflow implements the continuous integration pipeline that runs on pull requests to main and pushes to dev, validating dbt installation and preparing a test warehouse so changes can be tested before they reach main.
- **`DuckDB warehouse setup step`** (in `dbt-ci.yml`) — The inline steps that create a CI data directory and a DuckDB warehouse file with a bronze_products table and a test row provide the lightweight, local test data context the CI job needs to run dbt tests and builds.

## Architecture Notes

The directory is organized as a pair of GitHub Actions workflow files, each defining a separate pipeline: dbt-ci.yml provides a continuous integration pipeline that runs on pull requests to the main branch and on pushes to the dev branch, and dbt-cd.yml provides a continuous deployment job that runs on pushes to the main branch. Both workflows prepare a local DuckDB-based warehouse and a small test dataset and both install dbt for DuckDB and set up Python 3.12, so each file contributes a self-contained automation sequence for a distinct stage of the development lifecycle (CI vs CD). A reader should approach dbt-ci.yml to understand how changes are validated in pull requests and dev pushes, and dbt-cd.yml to understand how changes are built and deployed on main.
